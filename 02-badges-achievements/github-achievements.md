# GitHub Achievements and Profile Highlights

GitHub profile achievements are small visual signals of participation. They can make a profile more interesting, but they are not a substitute for useful work, clear documentation, or respectful collaboration. GitHub changes achievement names, criteria, and availability from time to time, so confirm current requirements in the official GitHub documentation and on your own profile.

## Quick reference

| Achievement or highlight | General idea | Beginner-safe path |
|---|---|---|
| Quickdraw | A qualifying issue or pull request is closed quickly after opening. | Use a clearly labelled practice issue in a repository that welcomes it; never create noise in an unrelated project. |
| Starstruck | A repository reaches a required star milestone. | Publish something useful, document it well, and share it only with people who may benefit. Never buy or exchange stars. |
| Pair Extraordinaire | A merged contribution includes meaningful co-authorship. | Pair with another contributor when both people actually contributed and agree to the attribution. |
| Pull Shark | Qualifying pull requests are merged. | Make real, focused pull requests that solve a documented problem. |
| Galaxy Brain | Helpful answers are accepted in eligible discussions. | Answer questions you understand and verify the answer before posting. |
| YOLO | A qualifying pull request is merged without a review approval. | Use only a repository you control or a project whose rules explicitly allow it; never bypass review on someone else’s protected code. |
| Public Sponsor | Public sponsorship activity is recognized by GitHub. | Read the current GitHub Sponsors rules and make any financial decision voluntarily. |

Some historical or limited-time achievements are not earnable today. Examples include event-specific or archival achievements such as Mars 2020 Contributor and Arctic Code Vault Contributor. A missing badge is not a failure; it may simply be unavailable.

## How to participate responsibly

1. Read the repository README, contribution guide, issue templates, and code of conduct.
2. Choose a useful task instead of manufacturing activity for a metric.
3. Keep practice work in your own repository or the included sandbox.
4. Never spam issues, duplicate pull requests, pressure maintainers, buy stars, or expose credentials.
5. Verify current achievement criteria before relying on an old tutorial.

## Profile highlights

Profile highlights and badges can represent GitHub Pro, Developer Program membership, Campus Expert participation, security work, or other programs. They are separate from repository README badges. Eligibility often depends on an application, a paid plan, a recognized program, or an accepted security contribution. Read the relevant official program page before applying.

## Repository README badges

README badges, often called shields, communicate project status such as build health, coverage, release version, documentation, or license. They should be accurate, accessible, and maintained. A badge is useful when it answers a reader’s question; remove badges that are broken or misleading.

Example Markdown:

```markdown
[![Build](https://img.shields.io/badge/build-passing-brightgreen)](URL_TO_BUILD)
[![License](https://img.shields.io/badge/license-MIT-blue)](../LICENSE)
```

Use meaningful alt text and link each badge to the page that explains the status.

## Practice guides

### Quickdraw-style practice

Use an issue in a repository you control or a designated practice repository. Open a clearly labelled test issue, wait for the practice instructions, and close it. Do not perform this exercise in a project where it creates work for maintainers.

### Pull Shark-style practice

Create a public practice repository, make a small meaningful change on a branch, open a pull request, run any checks, and merge it according to the repository settings. Repeat only when the changes are genuinely useful. The exact number of qualifying pull requests can change.

### YOLO-style practice

In a practice repository you own, create a pull request and merge it without a review approval only if the repository settings and your learning goal make that safe. Never treat this as permission to bypass required review in a community project.

### Starstruck-style practice

Build a useful project or resource, write a clear README, make it easy to run, and share it in appropriate communities. Do not request artificial stars, use star exchanges, or present stars as proof of technical quality.

### Galaxy Brain-style practice

Find a genuine unanswered question in an eligible discussion, read existing replies, write a precise answer, and include evidence or a reproducible example. An accepted answer depends on the question owner and the discussion rules.

### Public sponsorship

GitHub Sponsors and other funding services involve real money. Review the service terms, privacy implications, and your own budget. Sponsorship is optional, and no achievement is worth financial pressure.

## Does an achievement help a profile?

It can show that someone participates in collaboration, but people evaluating a profile should also look at project quality, documentation, communication, and sustained learning. A small set of well-explained projects is usually more informative than a crowded badge collection.

## Change emoji skin-tone preference

GitHub’s interface may provide an emoji skin-tone preference under account appearance settings. Open your profile menu, choose **Settings**, open **Appearance**, and look for the emoji preference. Interface labels can change; if the option is absent, search the current GitHub settings documentation.
